# 分母提取器的变异红证

> 治理记录:`TCRN-TMS-STORY-003`(Epic `TCRN-TMS-EPIC-001`)· 分解裁定 minutes `TCRN-TMS-MIN-001` · 门 `TCRN-TMS-GATE-001`

## 规则

**一个从未见过红的检查器不可信。** 每个分母提取器在被用于任何覆盖率声称之前,必须先注入一个真实变异并实测它确实检出变化。本文件记录已完成的红证。

纪律三条:

1. 变异必须**真实改变字节**并在运行期生效 —— 一个不改变任何东西的「变异」证明不了任何事。
2. 变异后必须**无条件还原**,并验证还原后与原始字节一致。
3. 红证结果**只对被测的那个提取器成立**,不外推。

### 变异 4 的第一次尝试是一次自捕的假阴性(务必保留)

第一次红证尝试用 `perl -pi -e 's/398 条 handler/397 条 handler/'` 施加变异,随后 `--check` **返回绿、退出 0**。

看上去像门失灵,实际是**变异从未生效**:产物里的原文是 `**398** 条 handler`,数字两侧有 markdown 加粗标记,正则匹配不到。门当时是对的 —— 文件确实没被改过。

改用先算哈希、断言字节确已改变、再跑门的做法后,门立刻见红。

> **一个没有先证明自己生效的变异,证明不了门的任何事** —— 它给出的绿和门坏掉给出的绿完全无法区分。
>
> 这正是 `scripts/facts-mutation-red-proof.mjs` 里那句 `if (mutated === original) throw new Error("变异未改变字节 — 变异本身无效")` 存在的理由。本次是在**没走那个脚本**的临时手测里栽的 —— 纪律写进脚本还不够,手测也必须遵守。

## 两个必须写进门的教训

### 一、只比计数的门是假门

变异 2 把 `tenant.manage` 改名为 `tenant.manage.MUTATED`。**资源计数纹丝不动:46 → 46。** 只比较计数的门会直接放行,而实际上权限词汇已经被改。抓到它的是**排序后清单的内容 sha256**。

> 分母门一律比对内容哈希,禁止只比计数。

### 二、codegraph 索引不重建就是假绿机器

变异 3 向 `apps/api/src/app.controller.ts` 注入了一个真实的新路由。

- 解析源码的提取器(inventory 脚本):**398 → 399,检出。**
- codegraph 索引快照:**398 → 398,完全看不见**,且查询注入的路由名返回 0 条。

codegraph 的 SQLite 索引(默认文件名 `codegraph.db`)是一个**快照**,不重新索引就不反映源码变化。把它当作门的证据源而不先 `sync`,门会在源码已漂移的情况下继续绿。

> 任何以 codegraph 为源的分母,使用前必须先 `pnpm exec codegraph sync`,且该 sync 必须是门自身流程的一部分,不能靠人记得跑。

这两条正是本平台「六个假门」教训在 TMS 的复现 —— 区别只在于这次是在门被信任**之前**抓到的。

## 复现方法

```bash
node /path/to/mutation-red-proof.mjs
```

脚本对每个变异:备份目标文件 → 应用变异并断言字节确实变了 → 重算分母 → 无条件还原 → 校验还原后哈希与原始一致。任一步失败即报错退出,不留残留。
